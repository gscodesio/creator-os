# CREATOR OS — MASTER BUILD SPECIFICATION

## Complete Full-Stack Product, Functional UI, Backend, Database, Media, and Verification

## 0. Mission and Definition of Done

Complete the existing Creator OS application as a genuinely working, full-stack creator management system.

The core product principle is:

**“I create content. The system tells me what to do next.”**

Continue inside the existing repository. The frontend already exists, so improve and connect it rather than rebuilding it unnecessarily. Make the current interface functional, implement the backend and database, complete all required actions, and verify the finished workflows.

Do not stop after creating a plan, adding placeholder files, writing tests that only exercise mocked behavior, or achieving a successful build.

### Non-negotiable requirements

- Use Next.js for both frontend and backend.
- Use PostgreSQL as the only application database.
- Use Prisma as the ORM.
- Use Cloudinary for media storage and delivery.
- Keep the existing visual design and working components wherever practical.
- Start with a clean development dataset. There is no real production data to preserve and no need for legacy-data migration.
- Do not seed fake Topics, Content Assets, Tasks, or other demo records during normal startup.
- Default configuration and Settings are allowed; fake content is not.
- Every visible button, form, dropdown, filter, menu, link, and search field must have its intended behavior implemented.
- All important business logic must be controlled by the backend.
- Keep API requests and responses small.
- Use actual application data, not hardcoded demonstration metrics or fake integrations.
- Do not add unrelated features, duplicate infrastructure, or unnecessary fallback implementations.
- Continue working autonomously without asking for routine decisions.
- Report genuine blockers honestly. Never claim that the entire application is error-free or production-ready without sufficient verification.

A feature is complete only when its frontend interaction, server logic, persistence, validation, loading state, success/error handling, and relevant tests work together.

## 6. PostgreSQL and Prisma Data Model

Design a relational schema appropriate to the existing product.

Include the required entities and relationships:

### Topic

Store the actual topic, content type, category/subtype, topic status, creation/update timestamps, and other essential fields.

### Content Asset

Store the asset identity, content type, production status, title, descriptive information, source Topic relationship, parent asset relationship where applicable, and necessary timestamps.

### Platform Distribution

Store each platform delivery independently, including platform, scheduled date, platform workflow status, internal publication status, and the associated Content Asset.

### Task

Store stable task IDs, action stages, status, priority, due dates when applicable, and explicit Topic, Asset, and Distribution relationships.

### Settings

Persist publishing targets, buffer duration, task capacity, timezone, launch date, platform spacing rules, and relevant application preferences.

### Media Asset

Store Cloudinary identifiers and metadata, Google Drive references where applicable, associated Content Asset, media purpose, and timestamps.

### Calendar data

Derive calendar entries from persisted platform distributions when practical. Avoid storing a second conflicting copy of schedules.

Create additional models only where they support a real product requirement, such as authentication or task audit history.

### Database quality

- Use stable IDs and explicit relational references.
- Add appropriate foreign keys, indexes, and uniqueness constraints.
- Enforce useful constraints for unique derived child identities and related records.
- Use Prisma transactions for operations requiring atomic changes.
- Prevent duplicate Assets and Tasks when requests are repeated.
- Use a development seed only for required default Settings, not fake content.
- Do not use titles, array positions, or UI labels as primary identities.
- Do not create redundant fields when values can be reliably derived from canonical records.

## 7. Status-Driven Workflow Engine

Use canonical typed statuses and explicit allowed transitions. The backend must reject invalid transitions rather than silently forcing states.

### Topic lifecycle

`Idea → Planning → In Progress → Done`

- Idea and Planning Topics do not produce production Tasks.
- Starting production validates the Topic and creates or finds exactly one linked Content Asset.
- The relationship must be persisted using stable IDs.
- The first valid production Task must be generated.
- The Topic must never be marked published merely because production started.
- Follow the existing product definition for the In Progress and Done states consistently across the UI and backend.
- Repeated Start Production actions must not create duplicate Assets or Tasks.

### YouTube Long Video

`Topic → Script → Shoot → Edit → Export → Schedule → Publish`

Only the next valid action should be offered for the current production stage.

### Standalone Reel

`Topic → Script → Shoot → Edit → Export → Schedule → Publish`

### Derived Reels

Exporting one YouTube Long Video creates exactly three unique child Reel Assets.

Each derived child follows:

`Edit → Export → Schedule → Publish`

Required behavior:

- All three Edit Tasks become available when the master Long Video is exported.
- Every child has a stable parent/child relationship.
- Editing Reel 1 must not advance Reel 2 or Reel 3.
- Each child has independent progress and distribution records.
- Repeated exports or Task Engine recalculations must not create duplicates.
- If one or two children already exist, create only the missing child identities.
- Derived Reels are not independent Topics.
- A Derived Reel counts as ready inventory only after its own edit/export stages are complete.

### LinkedIn

`Topic → Write → Ready → Schedule → Publish`

Support both categories:

- Informative.
- Long Video Related.

Their frequencies must be configurable independently.

### Carousel

`Topic → Create → Schedule → Publish`

Do not add an unnecessary Ready stage.

### Common transition rules

Every mutation must:

1. Validate the requested operation.
2. Find the exact record by stable ID.
3. Check the current status and allowed transition.
4. Update only the appropriate related records.
5. Create the next valid Task where necessary.
6. Recalculate affected buffer counts and recommendations.
7. Return the small updated result needed by the UI.

If a transition is invalid, return an appropriate error without partially modifying unrelated records.

## 8. Task Engine: The Next Best Action

The central promise of Creator OS is that the creator should know exactly what to do next.

Tasks must represent real, actionable work.

- Maintain one authoritative Task collection.
- Today, Upcoming, and Completed are filtered views of that collection.
- Task identity must use stable IDs and explicit relationships.
- Task identity must not depend on titles, badge names, display labels, or array indexes.
- Completing a Task changes only the relevant workflow entity.
- The next valid Task should appear without duplicates.
- Recalculating Tasks must not lose completed progress.
- Today’s Tasks must respect the configured daily task capacity.
- Remaining tasks should be shown in Upcoming.
- Tasks must not appear before their prerequisites are satisfied.
- Preparation tasks should direct the user to create genuine Topics when buffer supply is insufficient.
- Creating a Topic must reduce the appropriate preparation deficit.
- Starting production must replace the relevant planning recommendation with real production work.
- There must be no dummy Topics or fake Assets generated to satisfy buffer calculations.

## 10. Buffer and Readiness Calculations

The Buffer feature estimates whether sufficient eligible content is ready for future publication.

Define one consistent date-window convention across Settings, Dashboard, Tasks, Buffer, and Calendar.

Prefer an inclusive start date and exclusive end date so a 14-day window represents exactly 14 dates.

### Readiness rules

- A YouTube Long Video becomes eligible for a ready buffer after export.
- A Derived Reel becomes eligible after its own editing/export requirements are complete.
- An in-production Asset is not automatically ready.
- A scheduled Asset is not automatically equivalent to an additional ready Asset.
- Already published content must not be counted as future ready inventory.
- Do not double-count one Asset because it has multiple distributions.
- Do not count a parent Long Video and its child Reels as the same inventory item.
- Do not count the same Topic or Asset twice.
- Derived Reel shortages must recommend producing prerequisite Long Videos, rather than creating fictitious Derived Reel Topics.

### Dates

Keep these concepts separate:

- Configured launch date.
- Actual effective current date in the configured timezone.
- Simulated current date when simulation is explicitly enabled.

Do not freeze normal operation to an old saved simulated date.

Before launch, calculate the configured launch window and prioritize preparation. After launch, use the effective current date for the rolling window.

Settings, Buffer, Dashboard, and Tasks must agree on quotas, available inventory, deficits, and recommendations.

If the Buffer shows a deficit that requires action, the Task Engine should expose actionable preparation work.

## 15. Scheduling, Calendar, and Platform Distributions

A Content Asset represents a piece of content. Each platform delivery has independent scheduling and status.

A single Reel may have separate Instagram and YouTube Shorts distributions.

Each Distribution should track its own:

- Platform.
- Scheduled date.
- Workflow status.
- Internal publication status.
- Required platform metadata.
- Relationship to the Asset.

### Scheduling constraints

- Block same-day publication of the same Reel to Instagram and YouTube Shorts by default.
- Enforce the configured minimum/maximum spacing.
- Use the configured timezone consistently.
- Validate scheduling on the backend even if the frontend already validates it.
- Prevent duplicate or conflicting distributions.
- Provide useful conflict messages and allow users to choose another valid date.

### Calendar

- Read calendar events from persisted schedules/distributions.
- Avoid a second conflicting manually maintained schedule source.
- Fetch only the requested date range.
- Make calendar navigation, views, filters, and event actions functional.
- Support scheduling, rescheduling, and opening relevant content details.
- Ensure all date labels and ranges are consistent with Settings.
- Fix hardcoded stale dates and incorrect-year displays.

### Scheduled-date reconciliation

Follow the existing product rule for internal status reconciliation:

- When a scheduled date is strictly earlier than the effective current date, an eligible Scheduled Distribution may transition to Published internally.
- A date equal to the current date remains Scheduled.
- A future scheduled date remains Scheduled.
- Reconciliation must be idempotent.
- Instagram reconciliation must not change YouTube Shorts or LinkedIn status.
- Aggregate Asset status must be derived from actual platform-specific states using a clearly defined rule.

**Important:** This internal status update is not proof that a post was published externally.

Do not claim automatic publishing on YouTube, Instagram, or LinkedIn. Real external publishing would require official platform integrations, credentials, authorization, and verified API implementations. For this scope, make scheduling and internal status tracking reliable.
